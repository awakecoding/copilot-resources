# Long-plan orchestrator

Entry: `/long-plan-orchestrator plan <goal>` generates or reviews a plan; `/long-plan-orchestrator execute` resumes exactly one approved task (`execute TASK-NNN` selects an eligible task); `/long-plan-orchestrator status` is read-only. Repeat `execute` to continue. These are skill invocations, not `.prompt.md` files. If intent is ambiguous, inspect whether `.plan/` exists and clarify only when the choice would change files. Do not treat `plan` as authorization to implement it.

## Plan / review

1. Inspect the project root, existing `.plan/`, repository status, relevant source/tests and user-provided goals. Gather name, outcome, major work, success criteria, scope and constraints from available context. Ask a few targeted questions **only** for decisions that materially affect architecture, scope, dependencies or safety; give options and a recommended default. Estimate task count/phases rather than demanding an arbitrary number. If asked just to review, report gaps and suggested changes without executing tasks.
2. Partition into logical phases with explicit phase prerequisites; give each task a unique `TASK-NNN` ID, measurable acceptance criteria, risk/mitigation, testing, expected file scope, estimate if meaningful, and dependencies. Validate that each dependency exists, precedes its dependent (or is in the same phase), and the graph is acyclic. Identify critical blockers, rollback/contingency, deferred work and project/phase definitions of done.
3. Write four **non-executable** file types under the project-root `.plan/`: `plan.md`, `tasks.yaml`, `state.yaml`, `phases/phase-NNN.md`. Use the [plan artifacts and state reference](references/artifacts.md) for minimum fields and synchronization. Do not generate `.plan/execute.prompt.md`; this skill is the repeatable entry point. Use relative paths, valid YAML and RFC 3339 timestamps; do not invent tasks or pretend unknown facts are confirmed. If `.plan/` already contains a plan, review it and propose scoped edits; do not overwrite its state or reinitialize progress without explicit authorization.
4. Verify task IDs, counts, phase order, dependencies, artifact consistency and file links. Present the plan and risks for review. Mark plan approval as pending in `plan.md`; record explicit approval there with scope/date when received, and revisit it after material replanning. **Wait for explicit plan approval before executing any task**; plan creation/review does not imply approval. Do not automatically commit.

## Execute / resume

1. Load `.plan/tasks.yaml` (task status source of truth), `.plan/state.yaml` (summary), `.plan/plan.md`, and the current phase file; inspect `git status` before edits. Compare each claimed completed task/phase with its acceptance evidence, test results and relevant actual files; do not infer completion just from a counter or checkbox. If artifacts are absent, malformed or disagree, stop and reconcile from observed evidence with the user rather than resetting them. `status` is read-only and reports phase/task totals, blockers and next eligible task.
2. Require explicit approval of the plan and of starting execution. On each invocation, announce the selected task, acceptance criteria, dependencies and intended change scope; if approval for this action is unclear, request it before changing production files. An explicitly requested approved `TASK-NNN` may override automatic selection **only** if eligible. Otherwise choose a pending task in the current phase whose dependencies are completed: prioritize high-risk/critical-path work, then stable ID order. Never move to a later phase until all earlier tasks and their phase criteria are complete. If no task is eligible, report the dependency chain/blocker instead of skipping it.
3. Execute **at most one task per invocation**. Set it `in_progress` with `started_at` before work and update derived counts. For an interrupted `in_progress` task, inspect actual files/tests and continue that *same* task instead of choosing another or reapplying changes blindly. Preserve unrelated user edits. Make scoped changes, verify acceptance criteria and relevant tests, and check regressions. Mark `completed` with `completed_at` and actual files only after verification; synchronize the matching checkbox and derived state counts. If blocked/failing, preserve partial changes, record a truthful reason/status, stop, and report what failed and how to resume; do not claim uncommitted changes were reverted.
4. Once the task finishes, check phase exit criteria against actual changed files/tests and all completed task records. If satisfied, mark that phase complete and advance `current_phase` in the **same** state update; otherwise leave the phase active. Project completion additionally requires every task and phase completed, acceptance/phase gates verified from actual files, and definition of done checked. Report progress, validation results, blockers and next eligible task. Reinvoke the skill for another task.

## Boundaries

- Scope all reads/writes to the selected project root and authorized task paths; resolve candidate paths and reject traversal, external absolute paths, symlinks escaping the root or surprising targets. Confirm before touching out-of-scope files. Never overwrite dirty user files blindly.
- Do not skip/unblock tasks, change task dependencies, or mark criteria met without evidence. A requested replan must maintain unique IDs, graph validity and count consistency; retain notes/history for completed tasks.
- Do not `git add .`, commit, push, archive, or delete tracking files automatically. If commits are requested, inspect diff/status, stage only this task's files and tracking changes, and leave unrelated changes untouched. Archive/retire `.plan/` only on explicit request after verified completion, with a reviewed exact file list; never use blanket recursive cleanup. Before any removal, check each exact path's current content/status and spare unrelated or user-modified files even if they are inside `.plan/`.
