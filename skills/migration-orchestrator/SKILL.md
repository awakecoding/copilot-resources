# Migration orchestrator

Entry: `/migration-orchestrator plan <migration>` generates or reviews the plan; `/migration-orchestrator execute` resumes the current approved setup task(s), execution batch, or cleanup task(s); `/migration-orchestrator status` is read-only. Repeat `execute` to continue. These are skill invocations, not `.prompt.md` files. If intent is ambiguous, inspect `.migration/` and ask only if the choice would change files.

## Plan / review

1. Identify project root and scoped migration target; inspect current code/tests and `.migration/` before changes. Gather migration name and goal, complete item identities/paths, transformation pattern, expected compatibility or rollout mechanism, test/monitoring gates, batch size and rollback. Derive counts and item lists from evidence where possible. Ask targeted questions only for missing decisions needed to make a safe plan. If inventory cannot be established reliably, report unknown items and pause generation rather than fabricating a complete list or count.
2. Plan **setup → execution → cleanup** with explicit success and rollback gates. Setup can include coexistence/feature flags when appropriate, target implementation, tests, observability and a **tested** rollback path. Execution transforms every inventoried item once in deterministic numbered batches; prefer 5–20 items per batch, allowing a smaller last batch or explicitly justified alternative. Sequence dependent items accordingly and verify old/new behavior as applicable. Cleanup is conditional on all items/batches completed, rollout and rollback window verified, and no remaining consumers of legacy code. Do not assume feature flags or production rollout exist.
3. Write four non-executable file types under project-root `.migration/`: `plan.md`, `inventory.json`, `state.json`, `batches/batch-NNN.md`. Use the [migration artifact and state reference](references/artifacts.md) for the minimum schema, counters and batch rules. Use project-relative paths, parseable JSON without comments, zero-padded names and RFC 3339 timestamps. Review an existing plan without overwriting its progress; for changed scope, reconcile inventory IDs and counts before editing.
4. Validate unique item IDs and batch assignments, coverage (every item appears exactly once), count/checkbox consistency, transformation/verification instructions and per-phase rollback readiness. Present risks and the plan for review. Record approval as pending in `plan.md`; record scope/date upon explicit approval and renew approval after material replanning. **Do not begin setup or any execution without explicit approval of the reviewed plan and current action.** Planning/review is not execution.

## Execute / resume

1. Load `.migration/state.json` (phase/counters), `.migration/inventory.json` (item status source of truth), `.migration/plan.md` (setup/cleanup task checkboxes), and the current batch file where relevant. Check `git status` and actual file/test evidence for completed items and gates: counters or checkboxes alone do not prove completion. `status` reports progress without modifying anything. If plan, inventory, counters or checkboxes disagree, reconcile from observed work and validation before resuming; never reset progress blindly. Do not permit a phase override to bypass prior phase gates.
2. Announce the precise next action, files/items and rollback. **Obtain explicit confirmation for that action before edits** (an explicit approval of this exact action in the current request qualifies). In setup/cleanup do at most two approved tasks per invocation; in execution do at most one batch. Update phase `started_at` and status when work begins. After each setup/cleanup task meets its checklist/tests, check its box and update derived state counters; phase transition only after all exit checks pass. Reinvoke the skill to continue.
3. For execution, open the first unfinished batch and verify inventory membership. Process items in stable listed order: inspect actual file/location (line numbers are hints), apply only the approved pattern, test and verify each change, then mark that item completed with timestamp in inventory and refresh state counts. If interrupted, inspect `in_progress` or partly completed items, skip already verified items and continue the *same batch* without duplicating transformations. On failure stop immediately, preserve truthful status and partial changes, record the item/blocker and recovery instructions; never claim failed work was reverted or completed.
4. Mark a batch complete in `plan.md` and increment its state count **only when all its items and batch checks pass against actual files/tests**; update `current_batch` to the next unfinished batch or `null` once done. Transition to cleanup only when every batch/item is complete and execution gates pass. Cleanup tasks (e.g., removing flags/legacy code, documentation, performance verification) require independent checks and may include destructive steps: inspect exact references/files, confirm no consumers remain and request separate approval for named removals. Do **not** delete `.migration/` or archive its artifacts automatically; retain the audit trail unless explicitly requested after verified completion.
5. Report phase, completed tasks/batches/items, validation results, last action, blockers, rollback option and next step. On failure provide exact item/task, cause, impact and where to resume. Do not advance on an error.

## Boundaries

- Normalize/resolve paths relative to the selected project root. Reject path traversal, external absolute paths, symlinks escaping the root, missing or surprising targets. Never transform unrelated files or overwrite dirty user work without review.
- Do not silently skip items, batches, phase gates, or unverified rollback checks. Changing batch size/membership mid-flight requires a reviewed, explicitly approved replan preserving completed item history.
- No automatic `git add .`, commits, pushes, broad deletion or recursive cleanup. If requested to commit, inspect diff/status and stage only this migration's changed files/artifacts. For any archive/deletion present an exact path list and require explicit approval; inspect each target's diff/status first, preserve unrelated or user-modified files even inside `.migration/`, and never remove the only copy of state.
